v0.2-alpha-31: strip verbatim `\\?\` prefix from scanned project paths

User-reported bug from the v0.2-beta msi manual verification
(2026-07-08): the chat-view hero card for new sessions renders the
project path as `项目: hermes-tray (\\D:\work\workspace\hermes-tray)`
instead of the cleaner `D:\work\workspace\hermes-tray`.

Root cause: `Path::canonicalize()` on Windows always returns the
verbatim path form `\\?\D:\…` to bypass the legacy 260-char
MAX_PATH limit. `scan_project` was storing the canonical string
verbatim — the prefix is invisible to .NET/Win32 APIs but a
frontend `D:\…` consumer expects the un-prefixed form. The leading
`\\?\` re-appeared in `to_string_lossy()` and was returned to the
TS side via Tauri's JSON-RPC bridge.

The user saw two `\\` characters because each `\` in the Rust-side
verbatim string is one literal character — `\\?\` is two
backslashes plus `?`. The screenshot's renderer smudged the `?`
char (some Windows fonts or anti-aliasing drop it at low DPI),
which is why the user described it as "乱码".

Fix: `src-tauri/src/db/project.rs` adds a `strip_windows_verbatim_prefix`
helper that drops the leading `\\?\` while preserving the `UNC\`
marker for network-share paths (which canonicalize adds verbatim
for paths longer than MAX_PATH). The helper is wired into
`scan_project` so every persisted `project_context.project_dir`
now stores the regular `D:\…` form (or `\\server\share\…` for UNC).
